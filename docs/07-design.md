# 07 · 设计笔记

给要改模块内部的人看。每条"为什么不那样做"都对应一个已经踩过的坑。

---

## 验收标准只有一条

> **改游戏侧的任何一条规则，`scripts/` 里不需要改一个字。**

不是"尽量解耦"，是可执行的断言。判据第 10 组做了两件事：

1. 同一个 `CellGrid` 类，注入不同 `merge_rule` / `accepts`，得到不同行为
   ⇒ 规则确实在容器外面。
2. 读 `cell_grid.gd` 的源码文本，断言里面**不出现** `ItemDef` / `max_stack` / `def_id`
   这类词 ⇒ 防止有人把游戏逻辑塞回来（包括"就加一个字段"）。

反过来检验也成立：demo 里所有关于名字、颜色、数量、上限、路由的代码，
全在 `demo/` 那一侧。这不是巧合，是照着这条线切的。

---

## 只认几何：一次真实的重构

第一版里模块有 `ItemDef` / `ItemStack` / `ItemDB` 三个类，"能不能堆叠"写成了
`ItemDef.max_stack`。看起来方便，实际上是把**玩法设计**焊进了容器：

- 换个游戏要改 `ItemDef`（名字、图标、上限全是那一款游戏的）
- 同一份代码没法同时服务"背包里的枪"和"网格上的建筑"
- 判据里全是物品定义 ⇒ 测的是"这套物品规则"而不是"容器"

现在只有一个不透明的 `payload: Variant`。容器对它的全部操作是：搬进搬出、
写进快照、还给你。没有一次读取、没有一次比较。

代价是"一堆 25 个木头占几格"要由游戏来切（`blocks_of()`，12 行）。
这恰恰是应该的：那是设计参数，不是几何。

## 为什么目录是扁平的

`scripts/` 下没有 `core/` `model/` `ops/` `data/` 这种分层。

那种目录的名字是**抽象深度**，每个人划得都不一样，而且会随每次改动漂移：
今天 `GridOps` 算 ops，明天发现它需要 `Placement` 就变成了 model。
半年后没人说得清 `data/` 里该放什么。

现在是八个文件 = **八个概念**，`class_name` 已经承担了命名空间：

| 概念 | 文件 |
|---|---|
| 几何 | `grid_shape.gd` |
| 一条占位 | `placement.gd` |
| 网格 | `cell_grid.gd` |
| 找位策略 | `place_finder.gd` + `first_fit_finder.gd` |
| 重排 | `repacker.gd` |
| 动作入口 | `grid_ops.gd` |
| 坐标换算 | `grid_layout.gd` |

Godot 没有 package 可见性、也没有模块边界检查，目录层级对语义零影响。
等某个概念真的长到 4+ 文件（比如将来要支持非矩形形状，拆 `shape/`）再开子目录。

这条与 ECS（Entity / Component / System）、GAS（Ability / Effect / Cue）是同一种读法：
按"是什么"切，不按"有多抽象"切。

## 唯一真相 vs 两张表

```gdscript
_items = [Placement, …]      # ✅ 只有这一份
```

不存 `M×N` 的稠密占位表。存了就是两张表，而两张表**迟早会分家**：

- 症状：某一格永远放不下（表里有、列表里没有），或者某块画不出来
- 这种 bug 不报错、不崩溃，只是"有时候不对"
- 分家的时机通常是某个异常路径（回滚、重排、读档）

现算是 O(块数) 的矩形相交判断。9×4 的背包最多 36 块，36 次比较对任何帧率都没影响。
用这点 CPU 换"不可能出现两个互相矛盾的答案"，是划算的。

`at_cell()` / `key_at_cell()` / `cells_of()` 因此是**查询**，不是第二份数据。

## 返回值只有两种形状

不是风格洁癖。第一版每个方法自己长一套字典，结果是：`move_to_cell` 失败时
**根本没有 `moved` 键**，而调用方在正常路径写 `res["moved"]` —— 一走到罕见失败分支就崩，
而且报的是 `Invalid access to property or key 'moved'`，看不出是哪次调用。

现在：

- **判定 → `String`**（空串 = 可以）
- **动作 → `Dictionary`**，成功与失败**键集合完全相同**，失败时附加字段取空值

判据第 14 组**逐个比对成功/失败字典的键集合**，并断言
`ok == true ⇒ reason == ""` / `ok == false ⇒ reason != ""`。
所以文档里那张返回表才敢写死。

例外只有两个，都是因为"回答的不是成没成"：`insert_all()` 返回没收下的数组，
`remove_at()` 返回取出的那一块。

## 两档策略：为什么不让 `move()` 自己重排

二维矩形装箱是 NP-hard。online（不动已有块）便宜但会把网格切碎，
offline（允许重排）能把"面积够但塞不进"救回来，代价是玩家看到位置跳动。

**两者都留着，而且分成两个函数**，因为位置跳动的代价必须**显式选择**：

```gdscript
GridOps.move(...)              # 拖拽落点、预览
GridOps.move_fitting(...)      # 整板搬运、「整理」按钮
```

如果让 `move()` 在失败时自动重排，会有两个后果：

1. 拖拽预览（`problem()`）与松手结果分家 —— 因为 `problem()` 不能预演一次洗牌
2. 玩家放一个 1×1 的小东西，整板突然重排，会以为出了 bug

`move_fitting()` 还额外做了一件事：`order` 里点名了 `cell` / `to` 时**不重排**。
玩家已经指着那一格说"放这儿"，"我把你自己挪开"不是他要的意思。

## 重排是怎么做的

`GridRepacker.plan()` 是**有限轮贪心**，不是 MaxRects。规模小到不值得上空间树
（9×4 = 36 格，最多几十块）。

```
四种排序键   area（面积降序）/ long_side（长边降序）/ perimeter / tall
  ×
两种评分器   tight（贴边接触面积最大 → 剩下的空位是整块的）
             bl（左上优先 → 位置稳定）
= 最多 8 轮，谁先成听谁的
```

几个关键决定：

**① 面积下界先判。** O(n) 求和，挡掉绝大多数"真的装不下"。
没有这一条，网格一满就要白跑 8 轮搜索，而结果必然是失败。

**② 多轮不是"贪心更聪明"，是"没有单一排序对所有人都好"。**
一堆 2×2 混着几条 1×4 时，按面积排和按长边排给出的结果完全不同，
而判断哪一轮能成只能真的跑一遍 —— 那就都试。

**③ 原位优先。** 把"原位"折算成一个额外的接触面优先权（`score()` 里 `s -= base`）。
能不动就不动，玩家看到的是"旁边挪了一下"，而不是"整个背包被洗牌"。
`moves` 也只统计**锚点或方向真的变了**的块。

**④ 返回布局，不直接改网格。**

```gdscript
var plan := GridRepacker.plan(grid, incoming)   # 只读，一行都不改
grid.restore(plan["layout"])                    # 全或无
```

于是"重排失败 ⇒ 网格一字未动"是白送的。`plan()` 可以随便试、随便推翻。

**⑤ 占用位图用内部类持有 `PackedByteArray`。** 那个类型是**值类型**，
当参数传进去再改，改的是副本，调用方看不见 —— 这个坑会让所有标记失效。
内部类 `_Board` 持有它，通过引用传 `_Board` 对象。

### 实测

9×4 网格，随机塞到 75%~95% 满，再试放一块，3000 个场景：

| 指标 | 数 |
|---|---|
| 直接放得下 | 51.6% |
| 直接放不下 | 1451 次 |
| └ 重排救回来 | **717 次（占失败场景 49.4%）** |
| └ 重排也失败 | 734 次，**全部**是面积真的不够 |
| `plan()` 耗时 | 平均 0.37 ms；观测最慢 1.9 ms；跑满 8 轮 2.8 ms |

**这张表不构成保证。** 几何上确实存在"面积够、形状无解"的情况
（判据里"9 个 2×2 塞 9×4"就是一例：面积正好 36，但 9 列是奇数铺不满）。
重排是启发式，只是在这套形状组合的随机场景里没漏过。

## `restore()` 为什么不问准入

`restore()` 刻意**不问** `accepts`：

- 存档里的东西本来就该待在它原来的格子里
- 规则改严之后（比如限制变多、堆叠上限降了），读档时把它们扔掉才是灾难
- 要不要清理是游戏的**存档迁移**逻辑（见 [06 · 坑](06-pitfalls.md#16-读档不清理被规则拒收的东西)）

这个决定带来一个后门，是写 demo 时才发现的：

> 两条重排路径（`insert_fitting` / `move_fitting`）都是借道 `restore()` 提交布局的。
> 于是"放不下就重排"变成了"把 `accepts` 拒绝的东西塞进去"的通道。

修法不是让 `restore()` 问准入（那会破坏上面的语义），而是把"收不收"和"放不放得下"
拆成两问：

```gdscript
grid.admits(payload)                    # 只有这一问涉及规则
grid.can_place_at(...)                  # 只涉及几何
```

然后在两条重排路径的**入口**先筛一遍。判据第 10 组 ③b 双向钉住：
重排必须被 `accepts` 挡住，`restore()` 必须放行。

教训：当两个语义刻意不同（读档 vs 放入），它们的共用路径就是后门的产地。

## 只支持矩形

没有 L 形、T 形、圆形。`GridShape` 里只有"宽 × 高"。

这是**明确的简化**，不是遗漏：

- 矩形装箱已经 NP-hard，非矩形要换数据结构（位掩码 / 多边形），
  拼装合法性判定也完全不同
- 绝大多数背包 / 仓库格子游戏就是矩形
- 保留升级路径：把 `Placement.cells` 换成"形状对象"，`GridShape` 加一组纯函数，
  `CellGrid` 的接口不用变（它只调用 `GridShape` 的判定）

同理只支持一次 90°：矩形转两次回原样，没有 180 / 270。
四方向的装备（比如斜放）需要另一套几何，别硬塞进 `rot`。

## 什么是"写 demo 时被固化进模块"的

边界不是一次画对的。做接入示例的过程中，有五样东西反复出现，于是从 demo 挪进了模块：

| 原本在 demo 里 | 为什么挪进模块 |
|---|---|
| `_cell_rect()` / `_cell_at()` 那十几行 | 每个接入方都要重写，而且最容易写错（点偏一格）。做成 `GridLayout` 后，"画在哪 == 点到哪"变成可断言的 |
| "先直放，放不下才重排" | 与玩法无关，纯粹是装箱策略的顺序 → `insert_fitting()` |
| "搬不动就重排目标" | 同上，搬运侧的同一条策略 → `move_fitting()`。它一开始写在 demo 的批量搬运里，症状是"背包明明挪一下就能放下，按钮却说放不下" |
| 快照里带 `payload`、形状用 `base` 而不是查表 | 否则读档依赖物品目录，热更新会让旧档"认不出形状" |
| `clear()` | 接入方每次写 `while not is_empty(): remove_at(0)`，发 N 次信号、重绘 N 遍。一次清空是**容器该有的原子动作** |

**反向也挪过一次**：`capacity_text()`（`"已用 3 / 36 格"`）原来在 `CellGrid` 上，
做 demo 时发现它是界面文案而不是容器状态 —— 换个游戏 / 语言就得改。
现在模块只给 `used_cells()` / `capacity()` 两个数。

**留在 demo、不该进模块的**：拖拽状态机与键位、皮肤与配色、"枪进箱子"这类路由、
堆叠上限与切堆规则。理由都一样 —— 换个游戏就得重写，放进模块只会变成一份
没人敢改的默认实现。

## 判据怎么读

```bash
godot --headless --path . --script res://tests/run_tests.gd
# 14 组 / 17412 条断言
```

不依赖任何插件，不起窗口，几秒跑完。分四类：

| 组 | 性质 |
|---|---|
| 1–11 | 手写边界：放入 / 旋转 / 搬运 / 合并 / 重排 / 存读档 / 坐标 / 准入 |
| 12 | 随机性质：300 步随机操作，每步都查不重叠 / 不越界 / 形状与方向自洽 / 块数守恒 / **位置索引与 placements 一致** |
| 13 | 重排性质：12 轮 × 25 次 `insert_fitting`，钉住"重排成功 ⇒ 新块整块放下" |
| 14 | 返回值契约 + "一个动作一次 `changed`" |

其中四组值得单独说：

- **第 2 组**：除了断言"2×2 里放 1×3"被拒绝，还**穷举所有锚点 × 两个方向**
  证明真的无解 —— 排除"是不是找位算法漏了"。
- **第 10 组**：payload 任意 Variant 都能用；不同 `merge_rule` 得到不同行为；
  准入不能被重排绕过（③b）；源码里不许出现物品概念。
- **第 11 组**：36 个格的中心逐个点回去、块的矩形刚好覆盖它占的格、缝隙与外框返回 `(-1,-1)`。
- **第 14 组**：键集合逐个比对 —— 这条是写给调用方的承诺。

另有一条 demo 冒烟（`tests/demo_smoke.gd`，9 组），跑的是模型判据测不到的**接线**：
跨板拖拽、拖到容器外、落在标题栏、同板拖动回归、目标装不下时两边不变、
整理按钮、批量搬运走重排、存档 → 清空 → 读档逐块比对、准入规则。

为什么单独做这条：模型全绿而"拖过去没反应"，是接线断了 —— 它不在模型的职责里。

## 已知取舍 / 没做的事

| 取舍 | 现状 | 什么时候该改 |
|---|---|---|
| `room_for()` 用副本真放一遍 | 精确、与 `place_auto` 同源；大网格 + 海量块时会慢 | 每帧调用，或网格 > 1000 格 |
| 重排是有限轮贪心 | 8 轮，不保证最优 | 需要"最优排布"（比如自动布局的仓库界面） |
| 键 = 下标，会漂 | 一次操作用键，跨帧用锚点 | 需要稳定 id 时，在游戏侧维护 `payload.id → key` 映射 |
| 没有 `resize()` | 用"新建 + `restore()`"扩容（见 [04](04-recipes.md#11-扩容--换尺寸)） | 频繁变尺寸（比如可升级背包做得很多） |
| 只支持矩形、只有 0/90 | — | 需要 L 形 / 四方向时，先改 `GridShape`（接口不变） |
| 重排不做动画 | 视图侧补间（见 [05](05-view.md#重排的过渡动画)） | 玩家反馈"洗牌太突兀"时 |
| `describe()` 说中文 | 失败理由也是中文 | 要做多语言时，理由改成错误码 + 视图翻译 |

最后一条值得展开：失败理由现在是**给玩家看的中文**。这在单人中文项目里是对的
（直接贴状态栏就能用），但要做多语言就得改。届时不要翻译字符串，而是给
`reason` 加一个 `code` 字段，视图查表 —— 那是一次破坏性改动，判据第 14 组会告诉你
哪些地方得一起改。

## 改模块之前的检查清单

1. 这条改动是**几何**还是**玩法**？玩法请放到 `demo/` 那一侧，或者用注入点。
2. 会不会破坏"一份真相"？任何"再存一份索引 / 缓存 / 位图"的提案，
   先想清楚两份数据怎么保持一致（现有答案：不存）。
3. 返回值是判定还是动作？判定返回 `String`，动作返回键集合固定的 `Dictionary`。
4. 会不会多发 `changed`？一个动作只发一次，发出点只有 `_did_change()`。
5. 失败时两边有没有变？判定与提交必须共用同一段计划。
6. 跑一遍判据 —— 尤其是第 10 / 12 / 14 组，它们专门防"回头路"。

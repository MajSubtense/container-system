# 02 · 概念

如果只记住一句话：**模块只认识"一个 m×n 的矩形，在网格的第几行第几列，朝哪个方向"**。
剩下的全是你的游戏。

---

## 三层，别混

```
你的游戏        物品表 / 数量 / 堆叠上限 / 颜色 / 名字 / 拾取路由 / 界面 / 输入
                 ↓ 只交出「一块 m×n、能不能转、payload 是什么」
容器模块        CellGrid / GridOps / GridRepacker / GridLayout
                 ↓ 只处理「矩形、格、方向」
几何            GridShape：旋转、相交、越界、展开成格
```

- **几何**不认识容器，容器不认识物品，物品不知道容器的存在。
- 依赖只有一个方向：`grid_shape ← placement ← cell_grid ← grid_ops`。
- `GridLayout` 属于模块但不属于几何 —— 它是"格 ↔ 像素"的换算，因为那是
  "画在哪"和"点到哪"必须共用的唯一一段数学。

---

## 一份真相：`placements[]`

```gdscript
_items = [ Placement, Placement, … ]     # 一块一条，按放入顺序
```

**没有第二份"占位表"。** 某一格被谁占着一律现算：

```gdscript
func key_at_cell(cell: Vector2i) -> int:
	for i in _items.size():
		if _items[i].covers(cell):
			return i
	return -1
```

为什么不存一张 `M×N` 的稠密表？因为两张表迟早会分家，而分家的症状极难查：
"这一格看着是空的，但就是放不下" —— 表里有、列表里没有。现算只多几次比较
（9×4 的背包总共 36 格），换来的是**不可能出现两个互相矛盾的答案**。

所以 `at_cell()` / `key_at_cell()` / `cells_of()` 是**查询**，不是数据源。
你可以随便问，它们不会记住任何东西。

---

## 一块的四个数

| 字段 | 例子 | 含义 |
|---|---|---|
| `base_cells` | `Vector2i(1, 3)` | **未旋转**的基准形状。这块东西本身长什么样 |
| `rotatable` | `true` | **几何属性**：这块矩形允许不允许转 90° |
| `rot` | `0` / `90` | 当前方向 |
| `cells` | `Vector2i(3, 1)` | **旋转之后**实际占的宽 × 高 |
| `anchor` | `Vector2i(2, 0)` | 左上角那一格（**不是中心**） |

不变式（判据每次随机操作都在检查）：

```gdscript
cells == GridShape.of(base_cells, rotatable, rot)
```

为什么要存两份形状？因为这一条要**自描述**：转方向只需要
`(base_cells, rotatable, rot)`，不必回头问物品表。于是换物品表、热更新、
读一份旧存档，都不会让已经放好的东西"认不出自己是什么形状"。

### 方向只有两个状态

矩形转两次回到原样，所以没有 180 / 270：

```
rot = 0   正放（base 的样子）
rot = 90  转过来（宽高互换）
rot = -1  这不是一个状态，而是"没点名方向"的入参约定
```

`rot = -1` 出现在**入参**里，不出现在 `Placement.rot` 里：

- `place_at(..., rot = -1)`：先试正放，放不下再试转过来。
- `move_to_cell(..., rot = -1)`：**保持原来的方向**（不是"自动挑"）。
- 拖动中的方向必须是具体的 `0` / `90`，否则预览画正放、松手时容器自作主张转一下，
  玩家会看到"幽灵块说谎"。

方的东西（3×3）和 `rotatable = false` 的东西，任何方向参数都拿不到旋转形状：
`rotate()` 会明确拒绝并给理由，不会"转了但其实没变化"。

---

## `payload` 是不透明的

```gdscript
Placement.payload: Variant      # 可以是任何东西
```

容器对它的全部操作是：**搬进搬出、写进快照、还给你**。没有一次读取、没有一次比较。

这条设计带来两个直接后果：

1. **同一个模块能服务完全不同的游戏** —— "背包里的枪"和"网格上的建筑"用的是同一份代码。
2. **规则注入必须从外面来** —— 因为容器自己不认识 payload，它没法判断"两块能不能合并"。
   于是有三个注入点（见下）。

判据第 10 组会拿**同一个 `CellGrid` 类**、注入不同规则，得到不同行为，
以此证明"规则在容器外面"。

---

## 键 = 下标，会漂

`placements()` 的下标就是"键"：

```gdscript
var p := grid.placements()[3]      # 第 3 块
var who := grid.key_at_cell(Vector2i(2, 1))   # 这一格属于第几块
```

`remove_at(1)` 之后，原来的第 2 块变成第 1 块、第 3 块变成第 2 块 ——
**键会前移**。所以：

- ✅ 一次操作内用键（拿起来 → 放下，这一小段里没人删东西）
- ❌ 把键存进变量、跨帧/跨事件使用（"我上次拖的是第 3 块" —— 它可能已经不是了）

跨帧要记住"是哪一块"，用锚点或 payload 重新定位：

```gdscript
var idx := grid.key_at_cell(saved_anchor)     # 或者拿 payload 去比对
```

有个例外值得知道：**同容器换位是交换两个锚点，不重排数组**，所以换位不会让键漂。
合并会让源那一块从数组里消失，后面的键会前移。

## 为什么没有「数量」

这是整个模块最重要的一条边界。

```gdscript
# ❌ 模块里没有这些
grid.add(stack)
grid.count_of(&"wood")
grid.total_weight()
```

因为 **"25 个木头占几格、切成几块"是游戏的规则**，而且它是设计参数：

- 上限 99 ⇒ 25 个是 1 块（`{"wood": 25}`，占 1×1）
- 上限 10 ⇒ 25 个是 3 块（10 / 10 / 5，占 3 格）
- 有些游戏按重量算、有些按体积、有些干脆不允许堆叠

如果模块里写了"按上限切块"，那每一款用它的人都要先改模块。所以分工是：

```
游戏：一堆 25 个 → 切成 3 块，每块 {"id": "wood", "count": 10}
容器：这 3 个 1×1 放得下吗？→ 放得下 2 块，第 3 块没地方
游戏：把没放下的那块留在地上
```

demo 里这一步是 `DemoItemRules.blocks_of()`。**它一共 12 行**，但它属于游戏。

同理，"块是原子的"：没有"搬 3 个过去"这种操作。一个格子里就是一个东西，
要拆堆就拆完再来放两块小的。

## 三个注入点

容器把"因游戏而异"的三件事做成了回调：

| 注入点 | 签名 | 空着时的行为 |
|---|---|---|
| `grid.finder` | `PlaceFinder` 子类 | `FirstFitFinder`（行优先 + 正放优先） |
| `grid.accepts` | `func(payload) -> bool` | 什么都收 |
| `grid.merge_rule` | `func(新来的, 已在场上的) -> Variant` | 永不合并 |

外加一个"容器根本不知道"的：**拾取路由**（这块东西该进哪个容器）——
在游戏侧写一行 `if` 就完事了。

`merge_rule` 返回**新 payload** 表示"能合"，返回 `null` 表示"不能合"。
它必须是**纯函数**：判定（`can_merge_at`）和提交（`merge_into`）会各问一次，
两次答案必须一致。

---

## 两档策略：便宜的那档 + 重排兜底

二维矩形装箱（2D rectangular packing）是 NP-hard。工程上分两种玩法：

| | online（默认） | offline / 重排（兜底） |
|---|---|---|
| 动的范围 | 只找空位，**不动已有块** | 把已有块全部拿出来重排 |
| 代价 | 便宜、可预测、顺序稳定 | 玩家看到位置跳动；最坏 8 轮搜索 |
| 弱点 | 会把网格切碎，最后落到"面积够但塞不进" | 慢，而且位置会变 |
| 入口 | `place_auto()` / `GridOps.move()` | `GridOps.insert_fitting()` / `GridOps.move_fitting()` |

**两者都留着，而且分成两个函数**，因为位置跳动的代价必须由调用方**显式选择**：

- 玩家盯着拖影松手时，东西不该自己重新排一遍 ⇒ 拖拽落点只用 `move()`。
- 拾取掉落到背包、玩家点"整理"按钮 ⇒ 可以用 `_fitting` 那一档。

`insert_fitting()` / `move_fitting()` 内部已经把顺序串好了：**先直接放/搬，
失败才重排**。所以它们不会为了"排得更整齐"无事生非 —— 只在真的放不下时才动手。

---

## 失败时两边一个字都不变

所有写操作都是"先校验、后提交"：

```gdscript
var res := GridOps.move(bag, chest, {"from": 2, "cell": Vector2i(0, 0)})
if not res["ok"]:
	# 此时 bag 和 chest 都跟调用前一模一样，包括方向
	print(res["reason"])
```

跨容器搬运的失败路径包含回滚：已经从来源拿出来了，目标放不下就**放回原锚点与原方向**
（不是"随便找个空位塞回去"）。

判定和提交共用同一段计划（`_plan()`），所以：

> `problem() == ""` ⟺ 同样的参数 `move()` 会成功。

这条在拖拽里是硬需求 —— 预览和结果必须同源。

---

## 一个动作一次 `changed`

```gdscript
signal changed
```

发出点只有一处（`CellGrid._did_change()`）。所以：

- `clear()` 清 33 块也只发一次，不是 33 次。
- `move_within` 的换位（动了两块）只发一次。
- `restore()`（整块板替换）只发一次。
- 失败的操作**不发**信号（什么都没变）。

界面订阅它重绘就够了，不需要自己维护"哪些操作要刷新"。
